# 摘要与明细核验

同一采购包可能在公告中披露一批设备的摘要，在附件中披露分项商品。直接拼接两份数据可能重复累计；金额相等本身也不能证明商品属于同一组。

## 查看与导出

打开工作台中的采购包，在“层级核验”查看候选摘要、明细、原文和逐项检查结果。已确认的关系在明细视图中折叠摘要，摘要仍保存在原文记录中。待核验的关系保留全部原文行。

原有标的列表、五场景统计、CSV和默认比赛三表继续使用原文口径。通过层级核验页的“下载当前数据集的明细三表”，或指定 `item_view=detail`，可导出分层后的视图；这是当前数据集的导出，不是仅导出正在查看的采购包。

```text
GET /api/projects/{id}?dataset_id=official-reference
GET /api/export/standard.xlsx?dataset_id=official-reference&item_view=detail
GET /api/export/quality.json?dataset_id=official-reference&item_view=detail
```

工作簿仍是比赛规定的三张表，列名、顺序和金额单位不变。质量JSON包含关系、定位、核验项和保留原因。`include_notes=true`会增加内部处理说明页，不用于要求严格三表的正式提交。

## 自动确认边界

首版仅支持能明确证明包含范围的跨文件关系：

- 同一个已识别采购包；摘要以一批、一套等整体单位计量。
- 原文明确说明“本项全部明细”等范围，并引用唯一附件；没有否定、另计或作废说明。
- 摘要和明细具有程序从实际解析输入中定位的原文片段；不是仅采用模型自行生成的引文。
- 至少两条明细有原文打印的下级业务编号，例如 `1-1` 对应 `1-1-1`、`1-1-2`；不把金额作为行身份。
- 已披露供应商一致，原文行定位不同，没有重叠摘要或未解决的嵌套层次。
- 每个总价都能在原文片段带“总价”“小计”等标识的字段中找到，且明细合计与摘要金额在0.01元内一致。不补算原文没有披露的数值。

不满足检查时保留原文，不以更少的行数冒充更高准确率。没有编号层次、只有泛称“详见附件”、供应商未披露、折扣计价或表格数值缺少可核验标签的情况，首版不自动确认。

程序定位的片段和哈希保存在公告快照的 `source_context` 元数据中，不增加业务数据库列。旧快照缺少该字段时仍可读取和导出；通过已有历史响应重新回放可重新定位原文，不需要产生新模型请求。快照和当前数据库记录不一致时，页面停止借用旧快照证据。

## 验证边界

自动化验证覆盖确认、冲突、重复行、缺失证据、多个摘要、旧快照兼容、批次快照导出和移动端操作。构造样例只用于检查规则与交互，不代表官方数据上的准确率收益。内置20篇历史样本用于兼容回归。

```powershell
.\demo\procurement\.venv\Scripts\python.exe -m pytest -q demo/procurement/backend/tests/test_item_hierarchy.py
npm --prefix demo/procurement/frontend run build
node scripts/verify_item_hierarchy.mjs
```

浏览器测试使用独立数据库并禁止模型HTTP，不修改业务库。真实效果仍需新增独立人工标注，比较采购包归属、明细召回、错误折叠和重复金额；当前不提供改善比例或官方得分承诺。
