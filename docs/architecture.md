# 系统架构

系统将文件解析、实体抽取、采购包建模与关系查询分开，前端通过`/api`访问FastAPI服务。

## 处理流程

1. 按公告UUID匹配HTML和同名附件包，上传文件先做路径、数量和体积检查。
2. 按文件内容识别真实格式，恢复表格、PDF、Office或图片文本，记录来源文件与行号。
3. 选择解析预检、历史响应回放或模型抽取。模型使用结构约束提示，回放缓存缺失时直接报错。
4. 校验采购包归属、字段和来源；跨文件重复按身份一对一合并，保留第二来源和冲突。
5. 将公告、采购包、商品和投标记录写入SQLite，再提供关系聚合及标准导出。

## 后端模块

代码位于`demo/procurement/backend/app`。

| 模块 | 职责 |
|---|---|
| `main.py` | API、上传、访问令牌、导出入口 |
| `jobs.py` / `ingestion.py` | 公告分组、持久化任务、进度、重试 |
| `parsers.py` / `ocr.py` | 格式识别、安全解包、内容解析与OCR |
| `extractor.py` / `prompts.py` | 模型请求、响应缓存、分块与结构提取 |
| `evidence.py` / `reconciliation.py` | 来源定位和跨文件事实合并 |
| `item_hierarchy.py` | 摘要与明细的证据约束核验、非破坏性明细投影 |
| `document_policy.py` | 区分成交明细、声明函与需求模板 |
| `database.py` / `models.py` | 数据模型、事务、迁移与入库 |
| `analytics.py` | 五个业务场景及图数据 |
| `exports.py` / `acceptance.py` | 三表生成、格式与关系参考核验 |
| `evaluate.py` / `batch.py` | 局部评测和批量处理命令 |
| `neo4j_sync.py` | 可选图数据库镜像 |

## 数据模型

| 对象 | 身份与关联 |
|---|---|
| 公告 `notices` | `dataset_id + notice_uuid`；保存输入哈希和结构化结果 |
| 采购包 `projects` | 公告下的独立采购包；保留源包名、采购单位和成交额 |
| 商品 `items` | 归属具体采购包；七字段、来源行和`related_sources`证据字段 |
| 投标 `bids` | 归属具体采购包；主体、中标状态、审查、报价及评分 |
| 批次 `jobs` / `job_documents` | 处理方式、进度、逐公告状态、错误、调用数和结果快照 |

内部金额单位为元，标准工作簿按模板换算为万元。缺失报价不是零；公告总金额不直接分摊至各包。同一公告重跑按UUID和采购包身份更新，历史批次保留快照。

摘要与明细的关联保存在派生视图中，原文行继续保留。默认接口和关系统计沿用原文口径，明确请求 `item_view=detail` 时才折叠通过全部检查的摘要。核验条件及限制见[摘要与明细核验](item-hierarchy.md)。

## 关系统计

共同竞标要求主体在同一采购包有效参与。明确审查失败者保留在原始投标记录中，但不计入有效共同竞标；未知非中标者采用保守口径。共同采购单位则要求每个选定供应商都曾与该单位有中标合作，允许来自不同历史采购包。

金额按采购包或商品明细去重累计，并单独报告未披露项。集团、分公司和近似名称不会自动合并。

## 前端与部署

Vue界面分为工作台、数据接入、标的检索和关系分析。表格优先呈现结果，ECharts关系网络按需加载。请求状态按数据集和查询条件管理，避免迟到的响应覆盖新结果。

SQLite是主存储，Neo4j为可选事实镜像。设置`RELATION_BACKEND=neo4j`后，五场景从图数据库读取采购包、投标和商品事实，继续使用相同业务聚合规则；镜像过期时返回503。当前任务调度按单Uvicorn worker设计；多进程部署需要额外的队列与任务协调机制。

可选RAG使用内置领域规则的BM25检索结果补充抽取提示；规则不作为采购事实来源，RAG与历史结构提示使用不同缓存。LoRA训练依赖和入口与应用服务隔离。
